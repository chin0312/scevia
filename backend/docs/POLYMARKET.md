# Polymarket provider integration

This note records the provider contract used by the Phase 2 backend adapter. Provider field and pagination descriptions below come from the current official v2 OpenAPI and Polymarket API documentation. A single controlled request to the documented example account returned empty v2 envelopes; it did not validate populated records or prove database ingestion against live wallet data. Automated adapter and PostgreSQL tests use deterministic responses.

Polymarket's trading wallet can be a proxy/smart account distinct from a signer or funder address. This adapter sends the explicitly entered account wallet as Data API `user`, lowercased for storage, and does not discover or combine signer, funder, profile, or browser-connected addresses. Where a row echoes `proxy_wallet`, the adapter validates its address format and case-insensitive match; malformed or mismatched rows are excluded and counted. If the user-scoped endpoint omits the wallet, the request identity is used without inventing another address relationship. A public address is not proof of ownership.

The Data API currently labels monetary values with names such as `usdc_size` and `entry_cost_usdc`. Polymarket's current trading collateral documentation describes pUSD (wrapped USDC on Polygon); those API field names are treated as provider valuation units, not proof of the historical on-chain token contract. The adapter does not claim a cash balance. Trade history does not supply a historical fee for each fill, so fees remain unavailable and today's schedule is not applied retrospectively. Public market responses separately expose market-scoped Gamma fee metadata: fee-free, known, incomplete or unknown; enabled flag, rate, exponent, taker-only semantics, rebate rate, USDC unit, source and retrieval time. The official current fee formula is price-dependent (`C × feeRate × p × (1-p)`); makers are not charged. The response does not claim rounding rules, effective date, historical fees or actual trade role where Gamma does not supply those facts.

## Numerical and operational handling

Polymarket's Data API returns many financial fields as JSON numbers. Node.js 24's JSON reviver source context preserves those numeric lexemes for known financial keys before decimal validation. That preserves the precision actually sent in the JSON response; it cannot recover rounding performed upstream. Canonical values are decimal strings and PostgreSQL `NUMERIC(38,18)`. Values beyond that storage precision are rejected rather than silently rounded.

Requests use fixed Data API, Gamma and CLOB hosts, an 8-second HTTP timeout, a 2 MB response bound, JSON-only parsing and redirect rejection. Provider 429/503 responses honor bounded `Retry-After` values within the sync budget. Numeric rate limits are not published as a stable guarantee; API terms allow limits to change. Public search/resolve/history routes have their own API rate limit.

Each sync stream commits its pagination cursor and durable checkpoint with its records. A first history import starts at second 1, uses provider cursors, and is capped by the account execution budget, page and record limits. Each stream receives a bounded share of the sync budget so a large trades backfill cannot indefinitely prevent later activity streams from advancing. Repeated sync overlaps the prior seven-day window. Content fingerprints group ambiguous source evidence without creating canonical fills. Identical evidence cannot establish multiplicity. Legacy fingerprinted fills need Phase 3 reconciliation. Cursor ordering, snapshot stability, late-arriving history and provider record identity remain provider limitations.

The positions stream is deliberately incremental rather than authoritative. It pages `OPEN` positions with a zero token threshold. An interrupted refresh restarts from page one so latest-success membership covers one attempt. Historical `CLOSED` pagination is independently resumable and never changes current quantity. Pagination can observe concurrent account changes and no snapshot version is returned. An explicit zero in a current holding observation is distinct from absence. The positions API returns the latest stored observation with `observationStatus` and `positionState`: observed in the latest successful refresh, not seen there, latest attempt incomplete, provider-reported zero/closed/redeemable/positive, or unknown. A missed prior row remains available as history/current-last-known data but is visibly stale; it is not asserted to be a confirmed current holding. Provider status, archived/redeemable/mergeable flags and provider-reported P&L remain separately exposed. Observation retrieval time is not a source mark time.

Each provider page reports upstream rows received, source rows retained, invalid rows and excluded account-mismatch rows. Sync runs also count canonical records persisted, exact source duplicates, unresolved records, overlap candidates and intentional exclusions. Unresolved records preserve minimal validated financial fields, source endpoint, account scope, timestamp/transaction/token identity and reason; arbitrary provider responses are not retained. These are source facts for later retry or Phase 3 reconciliation, not canonical fills. The checkpoint may advance after the row is retained or explicitly classified, but coverage for affected entities remains partial when unresolved or invalid rows exist.

Market upserts use source revision time and identity confidence. Missing values do not clear known title, event association, rules, outcomes or payout fields. Lower-confidence event identity does not reassign a market unless a newer market revision supports the change. More terminal lifecycle observations are not rolled back by older/incomplete observations. Event and market lifecycle remain separate. Gamma public-market identity also keeps event provider ID, event slug, market ID, condition ID, outcome instrument ID and API-version-specific asset ID distinct. Slugs and condition IDs are not substituted for provider event IDs.

Market search accepts `q`, `limit` (1–10) and `page` (1–100). It exposes `providerHasMore`, `totalResults`, `nextPage`, `continuationAvailable`, event enrichment errors and market truncation. Search does not enumerate the whole exchange. Event and market URL resolution accepts HTTPS `polymarket.com` or `www.polymarket.com` `/event/{slug}` and `/market/{slug}` paths and drops known tracking/referral parameters; unknown query parameters, fragments, credentials, other hosts and arbitrary paths are rejected. Calls still target fixed Gamma/CLOB hosts. Event URLs return multiple market candidates when present. CLOB midpoint observations are reference prices with retrieval time and null provider timestamp; price-history points keep provider observation timestamps, reject out-of-range values, and report invalid-point count and completeness.

Settlements, redemptions as accounting events, collateral balances, complete cash history, rebates and fees are not advertised as reconciled capabilities. Redemption, reward, split, merge and other unsupported accounting events remain `unreconciled` facts where `/v2/activity` supplies them. Phase 3 must reconcile those facts with trades, future provider data and any permitted chain evidence before publishing realized performance.

## Local controlled live check

Wallet modes register the explicitly selected public wallet under a development portfolio, sync it through the running backend, and read back the first page (up to 100 records per endpoint) filtered to that provider account. They require no Polymarket credential, but they write source and sync data to the selected local portfolio. Modes are `connectivity`, `populated`, and `repeat`; a separate `market-services` mode checks search and optional URL resolution without wallet registration. All modes are opt-in, local-only, and excluded from CI. Every mode requires `POLYMARKET_LIVE_DATA_AUTHORIZED=YES`; wallet modes also require local API credentials. This guard is an explicit operator attestation, not provider approval.

```bash
export POLYMARKET_WALLET_ADDRESS='0x...'
export SCEVIA_PORTFOLIO_ID='00000000-0000-4000-8000-000000000101'
export DEV_AUTH_TOKEN='your-local-development-token'
export POLYMARKET_LIVE_DATA_AUTHORIZED=YES
npm run verify:polymarket -- --mode=populated
```

The script only accepts the local API at `http://127.0.0.1:3001`. It labels API counts as first-page readback rather than totals. Populated and repeat modes fail if any first sync stream is partial/failed, required retained/persisted facts or source-scoped API readback are absent; repeat mode also requires an observed exact duplicate. Empty connectivity cannot satisfy populated acceptance. This demonstrates one selected account's observed data, not lifetime history or accounting reconciliation. Do not run it until the intended data use is permitted. The [Polymarket Terms of Use](https://polymarket.com/tos), effective August 11, 2026 when reviewed, restrict access to or use of Polymarket Data (including raw, derived, aggregated or anonymized data accessed through an API or otherwise) by entities that qualify as Capital Market Clients, including financial technology companies, and by market-data distributors, unless Polymarket agrees in writing; they separately restrict certain redistribution/commercial exploitation. Scevia's classification and the applicability of those terms require maintainer/legal review; this summary is not a legal determination. That unresolved authorization is the blocker to populated live validation in this task and to any public/commercial deployment until reviewed.

A completed position retrieval with unusable rows reports a partial attempt and does not advance usable freshness. For any run, activity fact occurrences count committed rows, including identical rows across pages. Counts are separate across resumed and repeated attempts and do not establish economic multiplicity.

## Phase 6 acquisition decisions

Protocol V2 uses the pUSD ERC-20 on Polygon, backed by USDC, and changes exchange contracts. Version a financial observation using its verified contract address and protocol generation when identifying collateral. Data API amounts carrying legacy USDC names are insufficient evidence for that inference. Existing USDC-coded compatibility fields must be treated as provider report units until reconciliation establishes their exact denomination. Do not infer a cash balance from aggregate value or derive actual historical fees from today's Gamma schedule. No third-party acquisition, enrolment or paid service is needed for this patch. Choose at most one supplemental raw-evidence source after an approved sample shows a gap that official APIs and statements cannot close. Validate pending, credited and final bridge movements separately to avoid counting the same cash movement at multiple layers.

### Finalized native collateral read

After confirming both Polymarket wallet-data rights and the selected RPC service's permission for the intended queries and retention, set `POLYMARKET_LIVE_DATA_AUTHORIZED=YES`, `POLYMARKET_POLYGON_RPC_AUTHORIZED=YES`, and `POLYMARKET_POLYGON_RPC_URL=https://your-approved-polygon-rpc` on the loopback development server. Reuse an owned, explicitly registered wallet source.

```sh
api=http://127.0.0.1:3001/v1
auth="Authorization: Bearer $DEV_AUTH_TOKEN"
curl -fsS -H "$auth" -X POST "$api/provider-accounts/$POLYMARKET_PROVIDER_ACCOUNT_ID/sync?scope=current"
curl -fsS -H "$auth" "$api/portfolios/$PORTFOLIO_ID/cash-balances"
curl -fsS -H "$auth" "$api/portfolios/$PORTFOLIO_ID/coverage?providerAccountId=$POLYMARKET_PROVIDER_ACCOUNT_ID"
```

Verify the returned `PUSD` amount against the approved wallet and the same finalized Polygon block. The reader verifies chain ID, uses the documented pUSD contract, verifies its decimals, and pins ERC-20 calls to the canonical finalized block hash. The stream requires an RPC endpoint supporting the finalized tag and EIP-1898 block-hash parameters. Wallet balance is independent of reconstructed cash, CLOB spendable balance and open order commitments. It supplies no historical flows, fees or trade attribution. Historical API USDC-coded fields remain provider report units. [Polymarket contract deployments](https://docs.polymarket.com/resources/contracts) · [Block-hash RPC parameters](https://eips.ethereum.org/EIPS/eip-1898)

A separately approved wallet and transaction may be checked with `npm run verify:polygon-receipt -- "$POLYMARKET_WALLET" "$TX_HASH"`. The command emits only pUSD transfers observed in the successful canonical finalized Polygon receipt and preserves chain, contract, transaction and log identity. It classifies each transfer as unresolved. The output can help reconcile a user export, while an isolated transfer does not determine contribution, redemption, bridge intent, execution identity, or fees. Automatic historical receipt-ledger ingestion remains open.
