# Phase 7 continuous tracking

The first tracking slice adds a PostgreSQL-backed worker to the loopback development server. The owner watches up to 20 native catalog markets per workspace. A public market has one schedule across all interested workspaces. A second loop syncs explicitly approved account IDs through the existing ingestion leases, checkpoints, bounded page limits and overlapping windows. It schedules current snapshots and historical streams independently. A quote change does not call account endpoints.

## Operations and API

Before enabling, record the provider permissions for collection, frequency, retention and display. The documented endpoints and rate limits are technical capabilities. The terms and any additional approval govern use. See [Polymarket terms](https://polymarket.com/tos), [Polymarket rate limits](https://docs.polymarket.com/api-reference/rate-limits), [Kalshi developer agreement](https://kalshi-public-docs.s3.amazonaws.com/Kalshi-Developer-Agreement.pdf), [Kalshi data terms](https://kalshi-public-docs.s3.amazonaws.com/kalshi-data-terms-of-service.pdf), and [Kalshi rate limits](https://docs.kalshi.com/getting_started/rate_limits).

Run `npm run db:migrate` locally. Set the existing provider-specific gates and then set:

- `CONTINUOUS_TRACKING_ENABLED=YES` on the loopback development server.
- `MARKET_TRACKING_RETENTION_DAYS` to the approved integer duration from 1 through 366. The bounded cleanup deletes expired shared references only. Saved scenario inputs are frozen. Historical requests can lose coverage once an eligible observation expires.
- `MARKET_TRACKING_INTERVAL_MS` and `ACCOUNT_TRACKING_INTERVAL_MS` for approved cadence. Defaults are five and fifteen minutes respectively. History jobs use four times the account interval before retry backoff.
- `TRACKED_PROVIDER_ACCOUNT_IDS` to an optional comma-delimited list of approved, owned source UUIDs. Kalshi additionally requires the established account and credential binding. A CSV bucket has no account poll.

Authenticated `PUT /v1/portfolios/:portfolioId/tracking/markets` replaces the watchlist using `{"markets":["<catalog market UUID>"]}`. Use an empty list to remove all watches. Watches use existing provider-native catalog records and verified settlement denominations. `GET /v1/portfolios/:portfolioId/tracking` returns market and account attempts, latest successful checks, failures, upcoming attempts and latest shared observation provenance. Use the quote clock for market references and the accounting response for valuation availability. A successful metadata refresh alone says nothing about quote freshness or cash. The existing per-account sync endpoint remains the manual path. Remove a local account ID from the allowlist and restart to unschedule it, or disable its source.

Jobs claim due rows transactionally. An expired claim can be recovered after restart. Failed polls back off with jitter. Market jobs time out at 15 seconds. Shutdown aborts market requests and waits for an in-progress bounded account sync. Closed, resolved and unknown markets move to hourly monitoring. No settlement follows solely from a status or expected date.

## Prices and financial state

The worker reads standard Kalshi book midpoints and Polymarket CLOB midpoints when Gamma identifies the exact condition and maps distinct native outcomes to CLOB tokens. The catalog must agree on denomination. Unestablished identities and absent prices produce no mark. Midpoints use the retrieval clock and leave the source observation clock null. Kalshi last trade fallbacks are excluded. Shared evidence is isolated from private financial records. Records deduplicate by instrument, asset, source and retrieval time, and an inconsistent price for that identity causes a retry. Late observations are retained without replacing newer reference timestamps.

Accounting, risk and new scenario previews can consume the projected mark using existing canonical, denomination-matched financial evidence. Explicitly mapped CSV portfolios can benefit from shared market updates. Demo holdings with exact native catalog matches can consume the same observation while maintaining simulated IDs and financial ownership. Eligible demo lifecycle evidence also flows through the shared worker and existing derived settlement path. Saved scenarios do not rebase on market changes. Historical routes use a prior eligible observation and bounded in-range observations, with the original timestamps. Cash, quantities, basis, source evidence and settlement authority remain with the canonical ledger.

This slice revalues on read using the latest eligible marks in a coherent database snapshot. It does not publish a materialized valuation or recompute on every poll. The current valuation endpoint can reuse the prepared financial state across quote revisions. Historical analytics still use canonical replay, and large scopes can reach the existing replay limits. Durable valuation materialization and authorized live streaming validation remain future work.

## Provider and cost decisions

Start with bounded polling over the existing PostgreSQL deployment. The [Polymarket market channel](https://docs.polymarket.com/market-data/realtime-data) is a candidate for higher-frequency shared delivery. [Kalshi WebSockets](https://docs.kalshi.com/websockets/websocket-connection) require an authenticated handshake. Kalshi streaming remains deferred pending a suitable authorized workload. The guarded Polymarket market stream is described below.

A five-minute cadence targets up to 288 market jobs per tracked active market per day before global scheduling, jitter and backoff. A successful open Polymarket poll uses a condition lookup and midpoint call. The scheduled Kalshi lookup skips fee metadata. At most three market jobs are picked each five-second loop per process. Ten consistently open markets sharing a five-minute cadence imply roughly 2,880 jobs per day across all their portfolios, rather than 2,880 per portfolio. Account requests depend on provider streams and pages, and initial catch-up is more expensive than overlapped runs. A single PostgreSQL deployment suffices for this fixture-backed implementation. No paid provider, second datastore or incremental infrastructure charge has been verified. Measure provider units, database bytes and operational cost before selecting a Beta cadence or paid service.

## Holdings, current valuation, and historical references

The enabled worker reconciles demand for the local owner's portfolios in pages of ten every 30 seconds. A pass considers open canonical positions, pending simulated entitlements, and recent provider snapshots that identify an instrument and asset. Disabled private sources are omitted. Automatic demand is separate from the optional 20-market watchlist. Owner-scoped `POST /v1/portfolios/:portfolioId/tracking/reconcile` runs the same reconciliation without calling providers. Workspace deletion removes its demand by foreign key. Position and source updates converge on the next pass. Select catalog markets through the manual watchlist for explicit scenario interest, including when there is no actual funded account.

The worker claims up to three market jobs per five-second loop. Standard Kalshi polling skips fee schedule lookup. The tracking response distinguishes request success, metadata time, latest eligible quote time, missing or partial outcome quotes, and verified resolution. Verified terminal evidence stops open-market marks from carrying into observed exposure. It does not post actual receipts. Persisted account rows report active scheduling separately from historical job status. Source activity is rechecked during ingestion pagination and before saving a fetched page.

For an approved captured demo, initialization registers compatible exact native catalog identities. The tracker observes closed and resolved states without growing the initialization manifest. The accounting view combines shared lifecycle evidence with the owned initialization and derives simulated effects through the canonical ledger. Verified standard Kalshi payout can advance simulated settlement, while missing payout keeps financial results unavailable. Polymarket cases outside the verified legacy standard CTF path require independently reviewed payout evidence through the capture workflow. The underlying hypothetical records and previously frozen scenarios remain isolated.

`GET /v1/portfolios/:portfolioId/tracking/valuation` returns current cash and holdings with financial revision, market revision, an explicit valuation time and a private ETag. Conditional requests can receive 304. The process-local bounded cache reuses the canonical ledger's prepared financial state while applying changed market references with the same valuation routines. Corrections invalidate the prepared state and ambiguous equal-time marks fall back to canonical replay. Restart reconstructs the cache from confirmed database evidence. The endpoint reads one repeatable-read evidence snapshot. It does not materialize or push portfolio updates in the background. Exposure and allocation remain available through their existing separately scoped endpoints.

Historical queries select the last original observation for each instrument, asset and UTC day, plus exact opening, closing and bounded cash-flow anchors. The chosen rows retain original timestamps and source provenance. Retention still bounds available history and can remove the only eligible opening mark when required. The API then exposes unavailable coverage or valuation rather than constructing a replacement price. A 180-day request backed by only 90 days of marks can still contain an initial gap.

## Bounded receipt review

After approved account acquisition, set `POLYMARKET_RECEIPT_DISCOVERY_AUTHORIZED=YES` in addition to the existing provider and Polygon RPC configuration. Run:

```sh
npm run verify:polymarket-account-receipts -- <owned-source-uuid> <from-ISO> <through-ISO>
```

Select an approved window of at most seven days. The script discovers up to twelve distinct candidate hashes from the owned source's persisted trades and activities. Output includes the candidate source IDs, finalized execution and fee evidence and an explicit review status. Compare exact chain, exchange, instrument, transaction and log identities against independent references. Transaction association alone does not establish one-to-one linkage or financial classification. The script does not write ledger effects. Keep the output private. Shorten the window when the result is truncated.

## Lifecycle knowledge, current snapshots, and streaming

Lifecycle evidence has its own PostgreSQL journal. It records meaningful transitions and the first equivalent check per UTC day, with trading windows, expected settlement, payout proof and retrieval time separately. A demo's managed financial records and market coverage are distinct. A financial history interval advances within the affected account and denomination only as far as its held markets' lifecycle evidence supports it. A stale sibling does not erase known cash or realized components and cannot inherit the fresher market's coverage. `GET /v1/demo` exposes separate per-market lifecycle, quote and payout coverage. A conflicting winner preserves the previously supported payout and exposes `resolutionStatus: "conflict"`, or requires review through the capture workflow. Automated simulated payout uses observed proof time. Explicit captured records may document retrospective settlement or a separately chosen simulated payout timestamp.

An optional `asset` query on `GET /v1/portfolios/:portfolioId/tracking/valuation` returns the existing scoped risk and allocation contract in the same repeatable-read snapshot as cash and holdings, along with account freshness and demo coverage. Observed and reconstructed positions remain independent. A 304 still reads evidence and computes revisions. It avoids transmitting the body and can reuse the prepared replay, but it is not a constant-cost change feed.

History selects the last original instrument observation per UTC day and exact eligible opening, closing and cash-flow anchors. The before/after cash-flow lookup is batched; work is bounded by scopes and boundary count, and the existing 5,000 projected-row limit remains explicit. Up to 366 days of quote retention may be configured only if the approved rights permit it. No data is recreated after expiry. A longer requested interval than retained coverage has an opening gap. Physical aggregate storage and high-cardinality replay remain workload-dependent follow-ups.

The optional shared Polymarket market stream uses the documented public endpoint and application heartbeat. It watches up to 100 uniquely matched tracked USDC outcome tokens, waits for a full book before accepting subsequent quote events, discards malformed or older frames, batches writes, and reconnects on loss, heartbeat expiry or roster changes. REST polling remains active for initialization, reconciliation and fallback. Stream health and observed quote freshness are separate. The path remains disabled without separate approval and has no authorized live deployment evidence. See the [official market stream contract](https://docs.polymarket.com/market-data/realtime-data).

## Independent market research and reporting currency

An owner can create or resume a simulation-only collection with `POST /v1/simulations` and access its scenarios through `/v1/simulations/<collection UUID>/scenarios`. These collections are separate from the tracked portfolio list and reject tracked-account operations. The same scenario evaluator, preview tokens, normal save paths and denomination bundles remain in use. Existing saved scenarios retain their URLs. Actual mode from the collection takes an explicitly owned `sourcePortfolioId`; its baseline is frozen in the collection and recapturing it requires the source to remain eligible. Scratch and future Replay need only user-defined hypothetical native capital. Selecting a reporting budget never authorizes funding or transfers.

Use the existing validated provider search, URL resolution and history routes to discover candidates. Then POST `/v1/market-evidence` with a provider and exact Kalshi ticker or Polymarket condition ID. The endpoint uses fixed provider services and persists independently eligible native identity and current references, including exact Polymarket CLOB-to-position mappings when the regular binary generation and denomination are established. It does not select a market automatically for a multi-market event. An authorized exact request can populate an initially absent market. Kalshi free-text search still covers the local catalog. The existing history routes provide provider history independently of tracking. Automatic archival backfill into the canonical store, broader event-title ingestion and new payout proof for PositionManager remain open.

Set `follow: true` on an exact acquisition to keep a 30-minute renewable, owner-scoped research interest. Use `DELETE /v1/market-evidence/<market UUID>/follow` to release it. Each owner can follow up to 20 markets. Research demand shares market scheduling with holdings and manual watches. It never schedules private account sync. Saved simulations do not create permanent market demand. Streaming uses separate verified CLOB subscription tokens for mapped PUSD outcomes. Capacity above a 100-token group rotates in catalog order with polling still active. Tracking reports reference coverage from persisted observations independently of feed heartbeat and metadata check status.

The owner's reporting preference defaults to USD and can be set through `PUT /v1/preferences/reporting` with USD, SGD, EUR, GBP or MYR. `/v1/fx/reference` exposes eligible direct, inverse and documented USD/EUR cross-rate legs. Current valuation reports reconstructed values and a separate reported selected-asset subtotal where eligible. It retains independent financial, market and FX revisions. An explicit currency on the existing performance route adds converted selected-denomination history and eligible cash-flow-adjusted returns. Current rates are never applied back through a historical series. Explicit scenario `reportingCurrency` freezes the rate evidence together with the baseline; normal evaluation continues to respect native funding. Converted joint settlement and a full mixed-denomination historical return series are unsupported.

Authorized loopback operators may enable `ECB_FX_REFERENCE_AUTHORIZED=YES` for the shared daily ECB reference feed. It refreshes on startup and checks hourly. The source publishes business-day indicative rates. The feed date is stored separately from actual retrieval. Review [ECB reference methodology](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html) and [reuse conditions](https://www.ecb.europa.eu/services/using-our-site/disclaimer/html/index.en.html). For eligible independently captured fiat history or stablecoin market references, set `FX_CAPTURE_IMPORT_AUTHORIZED=YES` and run `npm run fx:import -- /absolute/path/to/approved.json`. Supply a bounded JSON array of decimal-string rates with base, quote, source, methodology, observedAt and retrievedAt. The import does not accept parity assumptions as market evidence. See [Data Acquisition Strategy](DATA_ACQUISITION_STRATEGY.md) for the guarded USDC and exact-contract PUSD collectors, source preferences and required permissions. Retain original publication/acquisition proof and obtain permitted quote, lifecycle and FX retention before operating.

For acceptance, acquire a previously unknown real market using an approved exact native ID, verify both outcome mappings, request applicable history and confirm research release changes only research demand. Enable permitted ECB access and compare USD-to-reporting conversion against published references. Supply independent stablecoin market evidence for USDC and PUSD where conversion is expected. Then verify FX-only updates leave native balances unchanged, and saved scenarios retain their original rate references. Repeat the live provider, RPC, statement and demo checks above. No authorized real provider, FX, RPC, or WebSocket validation was performed for this change.

### Historical evidence and consolidated reporting

Use `retrospective` to put authorized archival market closes and FX rates at their established effective times. The store keeps their actual retrieval times. `knowledge` admits an FX rate only after its evidenced publication time, or after acquisition if publication is unknown. Archived market samples with unknown publication clocks remain retrospective-only in the ledger. Their actual retrieval and provider observation times are exposed for future knowledge-time eligibility. The consolidated route conservatively withholds knowledge-time values when a relevant import, provider record or correction was acquired later. It does not reconstruct every prior version of financial decisions or provider records. The existing native financial replay remains effective-dated.

`GET /v1/portfolios/<uuid>/analytics/reporting-performance?from=<ISO>&asOf=<ISO>&currency=SGD&evidenceMode=retrospective` computes native USD, USDC and PUSD states at a shared valuation grid and at the union of external cash-flow boundaries. It applies eligible FX before aggregating and calculating TWR and drawdown. Unsupported, missing and reported-only scopes preserve known subtotals while blocking complete NAV and affected returns. Unclassified provider flows remain ineligible. Gaps and work limits remain explicit, and the calculation does not average native returns. Current reporting still leaves reported and reconstructed components separate.

The FX loader selects relevant assets, the requested reporting currency, and the USD/EUR bridge within a bounded date range. The reference read supports a preferred approved source and explicit evidence modes. Different source observations are ranked deterministically; contradictory evidence from the same source, methodology and effective instant is a conflict. A stale direct reference may be exposed as last known, but is excluded from usable reporting totals. The current freshness window is five days for daily fiat and one day for market stablecoin references.

### Acquisition commands

- Enable `ECB_FX_REFERENCE_AUTHORIZED=YES` for approved daily business-day fiat collection. Enable `KRAKEN_USDC_REFERENCE_AUTHORIZED=YES` for separately approved hourly USDC/USD OHLC collection. An hourly run requests the documented pair and drops the open bar. These are indicative or observed market references, with separate clocks and no claim of executable rates.
- Set `FX_ARCHIVE_AUTHORIZED=YES` and run `npm run fx:archive -- ecb` or `npm run fx:archive -- kraken` after obtaining the applicable permissions. ECB requests its 90-day archive. Kraken requests daily bars and retains up to the most recent 365 committed points returned by the source. The endpoints are fixed. ECB records use a stable source date for identity. When only an archive date is known, retrospective valuation conservatively uses it from the following UTC day. Knowledge-time eligibility uses independently evidenced publication or actual retrieval. Import independently approved evidence with `npm run fx:import -- /path/to/file.json`; `publishedAt` is optional and requires source proof. Run the collectors with the approved `FX_REFERENCE_RETENTION_DAYS` to expire shared FX rows. Saved scenarios retain frozen evidence under the approved saved-result policy. An opt-in CoinGecko collector stores indicative exact-contract PUSD references where the source reports volume. Bounded historical capture uses `npm run fx:archive -- coingecko-pusd` after the corresponding permissions and Demo API key are confirmed. Market prices, contractual redemption references and scenario-only assumed rates must stay separately labeled. Review [ECB reuse terms](https://www.ecb.europa.eu/services/using-our-site/disclaimer/html/index.en.html), [Kraken terms](https://www.kraken.com/legal) and [Kraken OHLC documentation](https://docs.kraken.com/api-reference/market-data/get-ohlc-data) before use.
- After exact market registration, `GET /v1/market-references?instruments=<comma-separated UUIDs>` returns persisted references for up to 50 instruments with conditional ETag support. It requires a Scevia identity and works without a tracked portfolio. POST `/v1/market-references/history` with instrumentId, from and through. This acquires bounded daily Kalshi observations or one page of Polymarket historical data using the mapped native identity. The response returns an opaque continuation if provided, stored observations and explicit coverage. Repeating a recent exact request reuses shared evidence. It never implies continuous pricing.
- Scratch scenarios support revision-checked `POST /v1/simulations/<collection>/scenarios/<scenario>/refresh-references` with revision and asOf. Mixed bundles freeze automatic selected-currency references, plus any explicit hypothetical overrides, at preview. Saving compares the preview digest. Changes to global preference do not rewrite a saved bundle. Reporting conversion leaves native funding intact, and cross-denomination joint settlement stays unavailable.
- V2 mappings can be registered through a verified tracked native market observation as well as through explicit discovery. The registration checks the exact condition, event, provider, denomination and native position group. Where provider identity or labels remain unverified, the system does not infer a stream token.
